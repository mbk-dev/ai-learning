# Commit

Создавай понятные коммиты только из изменений текущей задачи. Применяй правила
целевого проекта: `AGENTS.md`, `CLAUDE.md`, соглашения Git и обязательные проверки.

## 1. Проверить разрешение

Поручение «исправь ошибку» разрешает правку, но само по себе не разрешает commit,
push или PR. «Закоммить» разрешает локальный commit; «закоммить и запушь» — оба
действия. Ранее выданное разрешение действует в рамках задачи до выполнения или
отмены: повторно не спрашивай. Учитывай также явную проектную политику доставки.

Если разрешения на следующий шаг нет, сначала подготовь результат и покажи diff
и проверки, затем запроси конкретное действие. Не добавляй push или PR к просьбе
о локальном коммите. Слияние и deploy выполняй только в разрешённом объёме.

## 2. Изучить изменения

Работай в отдельной ветке/дереве задачи по правилам проекта. Уже выделенное дерево
не создавай повторно. Если деревья управляются Orca, используй её штатные команды.

```bash
git status --short
git diff
git diff --cached
```

Проверь рабочие и уже добавленные изменения. Чужие файлы и строки не включай,
не откатывай и не убирай в stash. При смешанных изменениях отбирай свои фрагменты
или работай в отдельном дереве. Неизвестного владельца изменений сначала выясни.

Разные независимые задачи раздели на отдельные коммиты. Связанные код, тест и
миграция могут составлять один логический коммит. Не добавляй секреты и случайные
временные файлы; учебные документы и таблицы не исключай только по расширению.

## 3. Проверить и создать коммит

Выполни проверки, требуемые проектом для окончательного diff. После правок
повтори затронутые проверки. Исправляй причины отказов hooks, не обходи их.

Добавь только выбранные пути и внимательно прочитай весь staged diff:

```bash
git add path/to/changed-file path/to/related-test
git diff --cached
git diff --cached --check
```

Не используй безусловное `git add -A`. Если индекс содержит чужую работу,
не выполняй обычный commit всего индекса и не сбрасывай чужой stage.

Сообщение составь по правилам проекта. При отсутствии соглашения ориентируйся
на существующую историю. Кратко назови изменение; при необходимости объясни причину.

```bash
git commit -m "fix: describe the change"
git show --stat --name-status HEAD
git status --short
```

Проверь фактическое содержимое созданного коммита. Не переписывай опубликованную
историю, не делай amend/reset и не удаляй lock автоматически при проблеме.
Ошибка прав доступа требует диагностики; sudo не является универсальным решением.

## 4. Доставить только по поручению

Перед push проверь нужные remote и ветку, а также все отправляемые коммиты:
вместе со своим коммитом можно случайно отправить чужую историю. Соблюдай
обязательный маршрут PR/review проекта и учитывай deploy от push.

При ошибке установи причину; не делай force-push или pull из master наугад.
Подтверди успешную отправку чтением удалённой ветки.

Если поручен PR, прочитай правила и шаблон репозитория, найди существующий PR
для тех же head/base и обнови его вместо дубля. Новый создай draft, если не
задано другое; состояние существующего не меняй. Опиши проблему, новое поведение
и существенные проверки. Сохрани ручные материалы описания и прочитай результат
обратно. Ошибка ответа на создание требует поиска результата, а не нового PR.

Сообщи SHA и сообщение коммита, выполненные проверки, статус push/PR и остаток.
Локальный commit не означает, что изменения опубликованы или развёрнуты.
