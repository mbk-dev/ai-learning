# Граф поведения агента

Опиши, как агент действует после события и при разных результатах. Граф помогает
найти пропущенные исходы и неограниченные повторы; сам по себе он не исполняет
процесс и не гарантирует соблюдение инструкции моделью.

Линейной процедуре без развилок достаточно списка. Применяй граф, когда нужны
повторы, ожидание, передача работы, восстановление или обращение к человеку.

## 1. Определить контракт

Установи цель, входное событие, наблюдаемые исходы, доступные операции и условия
завершения. Источники — поручение, инструкции проекта, интерфейсы и фактические
проверки. Не придумывай права, сроки или количество повторов.

Неустановленный предел обозначь параметром, например N или T, и назови его
неопределённым. До автономного исполнения нужное значение должно быть задано.
Ранее выданное разрешение учитывай в пределах задачи; граф новых полномочий
не выдаёт и повторного подтверждения уже разрешённого действия не требует.

## 2. Нарисовать состояния и переходы

Используй Mermaid `stateDiagram-v2`: узел — ситуация агента, а ребро — событие,
условие и короткое действие. Команды и подробности помести в текст под графом.
Топологию компонентов и поток данных можно рисовать отдельно через flowchart.

- Вход обозначь `[*] --> State`, завершение — `Final --> [*]`.
- Используй осмысленные id из букв, цифр и `_`; русские подписи задавай
  через `state "Ожидание результата" as Waiting`.
- Ветвление опирается на наблюдаемый факт: код возврата, поле ответа, проверенный
  артефакт. «Похоже, готово» не является критерием.
- Условия одного решения не должны пересекаться. Добавь ровно один запасной
  переход `[иначе]` или `[else]` на случай остальных результатов.
- Не используй `;` и HTML-подобные плейсхолдеры в подписи перехода: они могут
  изменить рендер. Длинные пояснения и пути оставь в тексте.

## 3. Ограничить каждый повтор и ожидание

Условие нового круга должно содержать предел: `[attempts < N]` или
`[elapsed < T]`. При исчерпании должна существовать ветка выхода.

В тексте укажи, где счётчик увеличивается, когда начинается отсчёт времени,
откуда взят предел и что остаётся после остановки. Повторный запуск ожидания
после диагностики тоже может образовать цикл: общий срок/счётчик не должен
обнуляться при каждом возврате. Само упоминание слова «таймаут» петлю не ограничивает.

Сохраняй исходные пределы и идентификаторы операций при восстановлении.
Неизвестный исход внешнего изменения сначала проверь чтением состояния;
не повторяй отправку, публикацию или создание ресурса вслепую.

## 4. Различать результаты процесса

| Префикс состояния | Результат |
| --- | --- |
| `Done_` | Цель подтверждена положительным наблюдением |
| `Handoff_` | Передача зафиксирована, известны получатель/источник продолжения и остаток |
| `Escalate_` | Агент остановился: требуется решение, доступ или участие человека |

Эскалация заканчивает текущий запуск. Ответ человека может начать продолжение
из явно описанной точки; нельзя молча снова отправлять тот же запрос по кругу.
Передача работы не равна её выполнению, а отчёт исполнителя не заменяет приёмку.

## 5. Добавить пояснения

Под графом опиши нетривиальные состояния: входные данные, действие, источник
наблюдения, проверку результата и сохранённые данные. Имена состояний в тексте
совпадают с id графа. Добавь раздел «Пределы»: каждое ребро повторного круга,
его условие и источник N/T. Не ограничивайся одним счастливым путём.

[Учебный пример с повтором и критериями приёмки](references/example.md).

## 6. Проверить

Сверь вручную:
- из входа достижимы предусмотренные состояния, из каждого состояния — финал;
- обработаны ошибки, неизвестные результаты, истечение срока и исчерпание попыток;
- на каждом цикле есть реально изменяющийся счётчик или общий срок и выход;
- Done означает проверенный результат, а не только отсутствие ошибки;
- внешние действия соответствуют существующим разрешениям;
- граф, пояснения и реализация описывают один процесс.

Для базовых **плоских** диаграмм в комплекте есть проверка на Python 3.10+
без внешних библиотек. Пути ниже указаны относительно каталога этого скилла:

```bash
python3 scripts/graph_check.py path/to/process.md
python3 -m unittest discover -s tests -v
```

Проверка читает все Mermaid state-блоки Markdown либо отдельный `.mmd`:
пустую схему, отсутствие входа/финала, тупики, недостижимые состояния, отсутствие
пути к финалу, развилки без fallback, несколько fallback, циклы без распознанного
предела и выход из Escalate. Код 0 — структурных находок нет, 1 — найдены либо
нет схемы поведения, 2 — ошибка вызова/чтения. Другие типы диаграмм пропускаются.

Это эвристика: сравнение `< N`, `<= N` или `≤ N` распознаётся как возможный предел,
но инструмент не доказывает изменение счётчика, смысл условий и фактическое
завершение. Составные состояния, fork/join и параллельные области не поддержаны;
их наличие возвращает находку. Для сложного процесса выдели отдельные плоские
подпроцессы либо используй подходящую проверку его полной модели.

Отдельно отрендери схему Mermaid и посмотри изображение: checker не заменяет
синтаксический анализ и визуальную проверку. Для кода сценарии тестирования
выводи из реально значимых переходов, включая ошибки и пределы; не подменяй
проверку поведения сравнением текста схемы с самим собой.
