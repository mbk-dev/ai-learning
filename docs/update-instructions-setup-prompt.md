# Промпт настройки update-instructions

Открой Codex или Claude Code на компьютере, где будешь работать. Скопируй
**весь блок ниже** в новую сессию. Клонировать этот репозиторий не требуется:
содержимое создаваемого навыка включено в промпт.

Промпт устанавливает пользовательский навык для текущего агента. Он сохраняет
знания и состояние задачи, а при явном полном вызове доставляет завершённую
работу по правилам проекта. Установка сама по себе не запускает доставку.

````text
Настрой на этом компьютере переносимый аналог команды преподавателя
update-instructions. Это поручение на установку навыка, а не на завершение
или публикацию текущего проекта.

Установи навык глобально для текущего агента, чтобы он работал в разных
проектах. Для других агентов ничего не устанавливай без отдельного поручения.
Не требуются API-ключи, MCP, сторонние плагины, серверы или инфраструктура автора.

1. Определи ОС, текущий агент, его версию, домашний каталог пользователя и
   активный профиль. Прочитай применимые глобальные инструкции и относящиеся
   к установке настройки. Не читай auth-файлы и не выводи конфигурацию целиком.
   Проверь существующие навыки update-instructions и команды update_instructions,
   включая симлинки и проектные версии: одноимённые навыки могут конфликтовать.
2. Для Codex используй пользовательский каталог ~/.agents/skills/update-instructions/;
   для Claude Code — ~/.claude/skills/update-instructions/. Учитывай настройки
   активного профиля и официальную документацию установленной версии. Если путь
   или механизм загрузки отличается, сначала установи фактический поддерживаемый
   вариант. Не устанавливай навык в профиль другого пользователя или харнесса.
   Существующий общий канонический каталог сохрани, не размножай копии регламента.
3. Сделай локальные резервные копии только затрагиваемых файлов вне Git и облака.
   Запиши, какие файлы отсутствовали. Идентичные файлы не переписывай. Для
   отличающегося навыка покажи существенный diff и запроси решение о замене;
   не заменяй более полную личную реализацию учебной. При неизвестном владельце
   или одновременно работающем установщике останови запись до выяснения.
4. Создай четыре файла из раздела «Содержимое навыка» ниже. Ссылки references/
   разрешаются относительно SKILL.md. Не добавляй зависимости на приватные
   пути автора, его память, скрипты, трекеры или обязательные инструменты.
5. В Codex навык должен вызываться как $update-instructions. В Claude Code —
   как /update-instructions. Для совместимости создай также тонкую команду
   ~/.claude/commands/update_instructions.md: она читает установленный SKILL.md,
   передаёт ему $ARGUMENTS и не содержит копию регламента. Укажи в ней фактический
   локальный путь. Существующий отличающийся алиас сохраняй до решения пользователя.
   Не создавай лишний одноимённый skill с другим разделителем в имени.
6. Чтобы автоматическое закрепление и восстановление были явным правилом,
   добавь в действующий пользовательский AGENTS.md (Codex) или CLAUDE.md
   (Claude Code) короткую ссылку на установленный SKILL.md и два указания:
   «После завершения содержательной задачи применяй автоматический режим
   update-instructions: только проверенные знания, без новых полномочий на доставку»;
   «После сжатия или возобновления читай точный checkpoint текущей сессии,
   если он известен, и сверяй изменчивое состояние перед продолжением».
   Сохрани прочие инструкции; не дублируй уже действующее правило. Учитывай
   AGENTS.override.md: не пиши в файл, который активный override перекрывает.
   При содержательном конфликте сначала покажи его и запроси решение.
   Проектные инструкции, модели, разрешения, sandbox и hooks не меняй.
7. Проверь YAML frontmatter, имя навыка, все три локальные ссылки и отсутствие
   незаполненных шаблонов. Если доступен штатный валидатор или проверка конфликтов,
   используй их и назови ограничения проверки; новые инструменты ради этого не ставь.
   Повторный проход установки без новых требований должен давать пустой diff.
8. Сообщи точные созданные/изменённые пути, резервную копию, выполненные проверки
   и способ отката только этих изменений. Не удаляй последующие правки пользователя
   при откате. Дай команды вызова и проверочный сценарий из этого документа.
   Загрузку навыка проверяй в новой сессии: наличие файла не доказывает discovery.
   Если открыть новую сессию нельзя, явно оставь эту проверку пользователю.

Это поручение разрешает перечисленные глобальные изменения. Подтверждение
нужно для конфликтов и действий за указанными границами; одинаковые файлы
и отсутствие конфликта не требуют повторного разрешения. Во время установки
не делай commit/push/merge, не запускай deploy, не меняй трекер и не выполняй
полный update-instructions над рабочим проектом.

### SKILL.md

```markdown
---

# Закрепление знаний и сохранение состояния

Работай только в границах текущего поручения и связанных с ним подзадач.
Правила проекта и ограничения пользователя сохраняются. Навык не повышает
полномочия, не разрешает обходить ревью, защиты веток или порядок доставки.

## Выбери режим до любых действий

- Явный полный вызов без ограничивающих аргументов: закрепи проверенные знания
  по [knowledge.md](references/knowledge.md), затем доставь всю завершённую
  работу текущей задачи и её подзадач по [delivery.md](references/delivery.md)
  в рамках действующего разрешения и проектного маршрута.
- --no-delivery: только knowledge.md; без commit, merge, push, enqueue,
  deploy, sync и удаления. Это распространяется и на репозиторий настроек.
- --checkpoint: только [checkpoint.md](references/checkpoint.md), без чтения
  процедур закрепления и доставки. Это не завершение задачи и не передача writer.
- Автоматически после содержательной задачи: только knowledge.md, без новых
  полномочий на доставку. Нет новых устойчивых знаний — не меняй файлы.
  Не запускай workflow повторно ради его собственного завершения.

При --checkpoint вместе с --no-delivery выполняй только checkpoint.
При сочетании checkpoint с просьбой опубликовать работу сначала сохрани
состояние; доставка — отдельный шаг в исходных полномочиях, не часть checkpoint.
Неизвестный аргумент или противоречивые требования уточни до записи.

Вопрос, цитата или обсуждение имени навыка не запускают ни один режим.
Знания храни в канонических документах проекта, процедуры — в навыках,
состояние задачи — в трекере/task state/checkpoint. Не копируй сырой диалог,
секреты или приватные сведения в публичный контур. Не редактируй внутренние
базы, сессии и автопамять харнесса вручную ради этого навыка.
```

### references/knowledge.md

```markdown
# Закрепление проверенных знаний

1. Начни с последнего подтверждённого прохода текущей задачи. Прочитай относящиеся
   к ней инструкции, индекс знаний и нужные первоисточники. Не обходи все проекты
   и историю. Включи результаты связанных подзадач; проверь реальные файлы/diff
   и evidence, а не только сообщение исполнителя. Недоступное отметь как пробел.
2. Отбери новые устойчивые решения, причины и подтверждённые неудачные подходы.
   Различай «предложено», «согласовано», «проверено» и «неизвестно». Статус
   текущей операции, временный блокер и весь журнал сессии постоянными правилами
   не становятся. Нет новых применимых знаний — заверши без изменений.
3. До записи найди прежние указания по смыслу и алиасам темы. Прочитай их условия,
   исключения и источник решения; изменчивые факты сверь в целевой системе.
   Новая дата сама по себе не отменяет принятое решение. Неразрешённый конфликт
   сохрани как UNKNOWN и покажи обе версии, не выбирая одну молча.
4. Используй существующий канон проекта. При его отсутствии достаточно Markdown
   в docs/knowledge/ с коротким индексом, создаваемым только при реальной записи.
   Устойчивые правила проекта идут в AGENTS.md/CLAUDE.md, повторяемая процедура —
   в соответствующий навык, знания — в документы, статус — в трекер/task state.
   Не раздувай всегда загружаемые инструкции подробностями одной задачи.
5. Обновляй существующее, не создавай дубли. При доказанной замене пометь старое
   правило устаревшим со ссылкой на новое и основание, сохрани происхождение.
   Укажи область действия, дату, источник и причину решения. Чужой канон вне
   полномочий оставь предложением, не переписывай его автоматически.
6. Проверь итоговый diff, ссылки и индекс, совместимость с действующими правилами
   и применимые проверки изменённых файлов. Перечитай записанное. Сообщи, что
   закреплено, что осталось спорным, какие области проверены и какие недоступны.
   Для --no-delivery закончи здесь; автоматический режим не добавляет разрешения
   на публикацию. В полном явном режиме перейди к delivery.md.
```

### references/delivery.md

```markdown
# Доставка завершённой работы

Этот раздел применяется при явном полном вызове и действующем разрешении
на соответствующие действия. Автоматическое закрепление его не включает;
--no-delivery и --checkpoint его не выполняют.

1. Для каждого затронутого репозитория установи цель, владельца, ветку/default,
   scope и применимое разрешение. Учти всё завершённое по текущей задаче и её
   подзадачам. Не включай чужую или незавершённую работу. Правила разных проектов
   не смешивай. Уже данное разрешение не запрашивай повторно.
2. Проверь готовность по DoD, реальному diff и нужным тестам. Сохрани чужие
   staged/untracked изменения. Закоммить только явные проверенные пути своей
   задачи. Перед push проверь всю отправляемую историю и секреты принятым
   механизмом проекта. Не обходи hooks и защиты ради успешной публикации.
3. Доставь результат в фактическую default-ветку штатным маршрутом проекта:
   PR, ревью, очередь слияния и/или deploy, если они требуются. Недостающее
   разрешение запроси для конкретного подготовленного действия. Не разрешай
   студенту самостоятельно сливать учебный PR, если это оставлено преподавателю.
4. Подтверди удалённый ref, merge и требуемый deploy живым чтением. Enqueue,
   одобрение или локальный commit не равны доставке. При неизвестном исходе
   сначала установи результат исходной операции, не повторяй её вслепую.
   Сохрани IDs/SHA/фазу; повторный вызов продолжает недостающий шаг, а не
   создаёт повторные PR, коммиты или deploy.
5. После доставки безопасно синхронизируй свои относящиеся к задаче деревья
   со свежим default. Служебный default обновляй только fast-forward; свою
   ветку — fast-forward или обычным merge по правилам проекта. Проверь status,
   diff HEAD, diff с origin/default и отдельно неопубликованную историю.
   Не применяй reset, force-push или stash к чужой работе ради чистоты.
6. Уборка идёт после проверки результата и по правилам менеджера worktree.
   До удаления нужны доказательства принадлежности, завершённости, доставки
   истории, отсутствия нужных процессов/удержаний и сохранности полезных данных,
   включая untracked, ignored и non-Git файлы. Активное дерево координатора,
   чужие и незавершённые деревья сохраняй. Нет доказательств — cleanup_pending,
   без удаления и автоматического снятия блокировок.
7. Закрывай связанную задачу только после её фактического DoD. В отчёте раздели
   local/committed/pushed/merged/deployed, укажи SHA и ссылки, sync своих деревьев,
   результат уборки и точные остатки. Незавершённую доставку успехом не называй.
```

### references/checkpoint.md

```markdown
# Быстрый checkpoint и восстановление

1. Используй доступные первичные источники текущей задачи. Не запускай новый
   аудит, сеть, workers или доставку ради checkpoint. Сохраняй один файл этой
   доказанной сессии в существующем приватном task state вне временного worktree.
   Иначе используй ~/.local/state/agent-checkpoints/<native-session-id>/checkpoint.md
   или эквивалентный приватный каталог состояния активного профиля в своей ОС.
   Настрой доступ только текущему пользователю доступным способом ОС.
2. Session ID возьми из runtime, не из имени вкладки; в Codex проверь фактический
   CODEX_THREAD_ID. Если ID неизвестен, используй уже установленный однозначный
   приватный путь задачи; если нет и его — сообщи пробел, не выдумывай владельца.
   Не выбирай latest и не читай чужие сессии. Зафиксируй exact path для resume.
3. Сохрани коротко: исходное поручение и scope; identity/владельца/UTC;
   worktree/ветку/HEAD; решения с источниками и статусом достоверности; сделанное
   и доказательства; действующие разрешения/запреты; незавершённые операции с IDs,
   неизвестными исходами, исходными сроками/счётчиками; ближайший разрешённый шаг
   и файлы для продолжения. Не копируй весь чат и секреты.
4. При повторе обновляй только смысловую дельту. Без изменений не переписывай
   файл ради нового timestamp. Записывай через временный файл и атомарную замену
   с проверкой, что прочитанная версия не изменилась. При конфликте сохрани свою
   версию отдельно в том же приватном контуре, не затирай другого writer.
5. Перечитай файл: identity, ограничения, UNKNOWN и следующий шаг сохранены,
   нужные локальные ссылки доступны. Сообщи exact path и оставшиеся пробелы.
   Не меняй постоянные инструкции, навыки, память, tracker state; не выполняй
   commit/merge/push/deploy/enqueue/sync/cleanup и не передавай право записи.

При resume прочитай явно переданный checkpoint либо файл текущей доказанной
сессии по установленному пути. Нет файла — восстанови состояние по обычным
источникам; отсутствие checkpoint само по себе не блокер. Сверь новые сообщения
пользователя и изменчивые факты, нужные для следующего шага, включая owner,
Git и исходы операций. UNKNOWN не означает «не выполнено» и не разрешает повтор.
Checkpoint не является новыми полномочиями, не заменяет текущие инструкции
и не передаёт writer. Продолжай прежнюю задачу в действующих границах.
Этот навык не устанавливает PreCompact hook: checkpoint запускается заранее;
автоматическое выполнение перед каждым сжатием не гарантируется.
```
````

## Проверка в новой сессии

Попроси агента показать найденный навык и его **фактический путь**. В Codex
выбери `$update-instructions`, в Claude Code — `/update-instructions`;
для алиаса проверь `/update_instructions --checkpoint`. В последующих примерах
замени имя вызова на вариант своего агента.

Используй отдельный временный учебный Git-репозиторий без remote и секретов.
Добавь один документ с правилом и его источником, оставь рабочую правку.

1. Вызови `$update-instructions --no-delivery`: новая подтверждённая находка
   должна попасть в документ знаний с источником, без commit и изменений refs.
2. Повтори вызов без новых находок: не должно появиться дублей или пустых правок.
3. Вызови `$update-instructions --checkpoint`: агент должен вернуть путь
   к прочитанному обратно checkpoint, сохранив исходную рабочую правку и refs.
   Постоянные знания и инструкции в этом режиме не изменяются.
4. В новой сессии передай этот exact path и попроси продолжить: агент читает
   checkpoint, сверяет живое состояние и не считает запись новым разрешением.

Отдельно проверь разбор трёх ситуаций без внешних операций: противоречащие
источники остаются спорными; вопрос «что делает update-instructions?» не
запускает доставку; полный вызов при обязательном преподавательском merge
сохраняет этот маршрут. Запиши реальные результаты и непроверенные пункты.
Наличие Markdown-файлов и статическая проверка не доказывают поведения агента.

## Источники и границы

Учебная адаптация команды преподавателя, предоставленной в поручении
16.11.2026. Личные скрипты, каталоги и инфраструктура автора не переносятся.
Регламент задаёт поведение агента; это не техническая блокировка операций.

Механизмы установки и вызова сверены с официальными руководствами:
[Codex skills](https://learn.chatgpt.com/docs/build-skills) и
[Claude Code skills и команды](https://code.claude.com/docs/en/skills).
Активный профиль и возможности установленной версии проверяются при установке.
